**Gap:** The owner, 2026-10-27, separated download from delete (ADR-028, replacing 2026-10-23's download-then-delete): *"Deleting and downloading aren't connected. If someone wants to delete their data, they can do it without downloading. If they want to download, they can do it without deleting. If they want to do both, they have to download first, then delete."* Downloads are stored files: *"The download should be hosted in R2 with an expiration (ideally a bucket age-out policy of 14 days). If the account is deleted after that, the data is lost. If not, they can request a new download. They can request a download twice per day."* (rolling 24 hours; a link in Settings and by email: *"Both"*; deleting the account deletes the download: *"Delete them together with a warning shown and a link to the download."*). S77 shipped the opposite: `GET /api/v1/me/export` returns the data inline with a 15-minute single-use deletion token, and `POST /api/v1/me/delete` refuses with 403 `export_required` without one. Nothing stores a download, limits requests, or sends email.

**Impact:** Before S80, someone had to download their data before they could delete their account, and the download existed only in that moment. S80 impact: downloading and deleting are separate choices; a download waits for 14 days, behind a link in Settings and in an email, and goes away with the account.

**Acceptance criteria** (checks `scripts/verify-S80.sh` performs)

1. Requesting a download, signed in, writes every registered store's `exportFor(uid)` (keyed by store name) to an `ExportStore` port in `packages/ports` with an expiry 14 days after it was made, and answers with its id and expiry, not the data; signed out it is 401 (test).
2. A third request inside any rolling 24 hours is refused with 429 and the time the next is allowed; a request 24 hours after the earliest of the two succeeds (test with an injected clock).
3. The user's current download (id and expiry) can be read, and its file fetched by its owner only: another user, an expired download, or none gets 404 (test).
4. A successful request sends one message through a `Mailer` port in `packages/ports` to the account's email, holding a link to BT and no exported data (test against the in-memory mailer).
5. `POST /api/v1/me/delete` deletes with the typed phrase and a recent sign-in alone, with no download made (test); its 403 `reauth_required` and 400 `phrase_mismatch` refusals are kept (test). The deletion token is gone: no `deletionToken`, `DeletionTokenRepository` or `export_required` remains under `packages/` or `functions/src/` (grep).
6. The `ExportStore` is registered in `personalDataStores()` as `Cloud storage: data downloads` and labeled in the classification manifest; deleting an account removes its downloads and request times, and another user's are untouched (test: the store passes the repository contract's deletion case).
7. In-memory `ExportStore` (honouring the 14-day expiry) and `Mailer` adapters live under `functions/src/adapters/memory/` and are what `pnpm dev` uses; no `console.*` call this story adds logs an email address or exported data (grep).

**Notes (2026-10-27 backlog review, at `63f5e62`):**

- **Where the manifest looks:** `data-classification.test.ts` discovers repository classes only in `functions/src/adapters/memory/repos.ts` (`/^export class (\w+)/gm`). Put `InMemoryExportStore` and `InMemoryMailer` there, or widen that discovery to every file in `adapters/memory/`, which is also inside the fence. Otherwise AC 6 and AC 7 pass with nothing checking their labels.
- **The dev mailer holds addresses.** If `InMemoryMailer` keeps the messages it sends (AC 4's test reads them), each one holds an email address, so it is personal data. A `none` label would be false, and `retained` is only for the deletion log. Register it under ADR-028's `Cloudflare Email` row, verbatim (S76's grader requires each `*_STORE` name to be a **Where** row). Its in-memory `deleteFor(uid)` drops that user's messages, so `Mailer.send` carries the uid. When the Cloudflare adapter lands, its own deletion and retention follow that row ("Cloudflare's retention"). If the mailer keeps nothing, label it `none` and say why.
- **Export without nesting:** `ExportStore` is itself a registered store, so its `exportFor(uid)` returns metadata only (ids, expiries, request times), never the stored files. Otherwise each download would contain the one before it.
- **One rule, in `packages/domain` (ADR-025):** the 14-day lifetime and the two-in-rolling-24-hours rule are pure, tested domain functions (for example `downloadExpiresAt` and `nextDownloadAllowedAt(requestTimes, now)`). The server returns `expiresAt` and the refusal's next allowed time, so S79 formats them and never recomputes.
- **The 429 body:** every 4xx in the spec is `ApiErrorResponse { error, hint? }` (`functions/src/services/openapi.ts` maps `errors` to it). To carry the next allowed time, add an optional field to `ApiErrorResponse` or give the route its own error type, and add `429` to the route's `ROUTE_DESCRIPTIONS` errors. An optional response field is not breaking.
- **Absolute link:** an email needs BT's full address, and locally the web app (:5173) and API (:8787) are separate. Read an app origin through the existing `SecretsProvider` / environment lookup (`adapters/fixtures/auth.ts`, `local-server.ts`), defaulting to `http://localhost:5173`. Link to `/settings` (`web/src/routes.tsx`, `SignedInOnly`), so S79 needs no new route.
- **No email address:** `UserProfile.email` is `string | null`. A download for an account without one still succeeds and is linked in Settings; no message is sent (test).
- **Removing the token:** `InMemoryDeletionTokenRepository` (`repos.ts`) and its manifest label, `DeletionTokenRepository` (`packages/ports/src/personal-data.ts`), the `deletionTokens` dep in `adapters/fixtures/auth.ts` and `services/account-deletion.ts`, and the delete route's 400 text in `openapi.ts` all go. `signed-token.ts` stays, because `session.ts` signs sessions with it; only the deletion-token purpose goes. Nothing in `web/src/` outside `api/generated/` uses the old routes, so no web code outside the fence breaks.
- **AC 5's grep:** ignored `coverage/` output holds stale copies (`packages/ports/coverage/personal-data.ts.html` names `DeletionTokenRepository`). Grep tracked files (`git grep`) or skip `coverage/`.
