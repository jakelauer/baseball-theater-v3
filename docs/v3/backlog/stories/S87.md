**Gap:** The owner wants the deletion message shown at `/settings`, *"triggered by visiting the settings page with a server-only cookie that is only sent to users after deletion"* (2026-10-29), shown *"Until seen once"*. A cookie the page's code can't read (`HttpOnly`) has to be set and read by the server: today `POST /api/v1/me/delete` sets no cookie, `GET /api/v1/me` answers a deleted user plain 401, and BT sets no cookies at all. The owner also made the cookie law a conscious choice (asked whether LAWS.md should gain it: *"Yes, add it with S87"*): cookies are set by one codepath only. Inserted by the owner, 2026-10-29.

**Impact:** Before S87, nothing could tell a browser that had just deleted its account apart from any signed-out visitor. S87 impact: right after a deletion the server remembers it once, privately, so Settings can show the deletion message on the next visit and then forget it — and any other cookie fails the build until the owner decides otherwise.

**Notes (2026-10-29 backlog review, at `aec31e6`):**

- **Ground truth:** S77 is `done`. `functions/src/handlers/api.ts` has `GET /api/v1/me` (`if (!account) return unauthorized()`, body `error: "unauthorized"`) and `POST /api/v1/me/delete` (400 `invalid_body` / refusal, 200 `{ deleted: true }`). Handlers return a web `Response`, so the cookie is a header on it, and the same code serves the Worker (S45). Nothing in `functions/src`, `packages/` or `web/src` sets or reads a cookie yet. `docs/v3/LAWS.md` has no P10 row (the owner removed the example on 2026-10-28). `scripts/backlog-vault/laws.test.ts` requires an enforced law's `Enforced by` file to exist and its `Step` to be in the `pnpm verify` chain, so a functions test is step `test:coverage`. `ApiErrorResponse.error` is a plain string in `openapi/bt-api.v1.json`, so documenting `account_deleted` breaks nothing.
- **The local Node adapter keeps one `Set-Cookie`.** `functions/src/adapters/node/http.ts` writes `Object.fromEntries(response.headers)`, which merges repeated headers. That is fine for the one cookie this story sets or clears per response. If any response ever needs two, use `headers.getSetCookie()` there; the file is inside this fence.
- **Fit with the SPA:** the API is same-origin (`baseUrl: location.origin`; in dev the Vite proxy passes `Set-Cookie` through, and with no `Domain` the cookie belongs to the page's host). A `SameSite=Strict` cookie goes with the page's own `fetch` even when the visit started from an outside link. A browser-session cookie fits *"Until seen once"*: closing the browser before visiting only loses a one-time message. The client changes S79 needs (calling `/me` with no token, reading the 401 body, one in-flight call under `StrictMode`) are in S79's notes, not here.
- **Personal data (ADR-028):** a fixed marker (AC 4) set after the uid is gone is not a store in ADR-028's inventory. It carries no personal field, it can't be traced back to the account, and it is cleared the first time it is read. Say so in `deleted-cookie.ts`'s comment and add no manifest entry. A value that identifies the account would need the owner to amend ADR-028 first.
- **P10 binds later work:** any later cookie (for example, a server-side sign-in callback when Logto lands) must go through `deleted-cookie.ts` or come with the owner's override (`docs/v3/LAWS.md` Overrides). The law's row should say so, so the story that brings the next cookie finds it.
